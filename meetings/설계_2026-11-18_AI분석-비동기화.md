# 설계 — 종목 심층 분석 AI 생성 비동기화 (2026-11-18)

## 0. 배경과 사실 확인

- 증상: 종목 심층 분석(StockInfo)에서 `EGW00133 접근토큰 발급 잠시 후 다시 시도하세요(1분당 1회)` 원문이 간헐적으로 화면에 노출된다.
- KIS 의 "1분 1회"는 **토큰 발급**에만 걸린다. 조회 API 는 실계좌 초당 19회(pykis `REAL_API_REQUEST_PER_SECOND`)까지 된다.
  발급된 토큰은 24시간 쓴다.
- 지금 오류가 나는 이유: 같은 KIS 앱키(1번 계정)를 쓰는 프로세스가 여럿이다(gunicorn 워커 4개 × 컨테이너 여러 개).
  pykis 는 토큰 파일 캐시를 **생성할 때 한 번만** 읽는다. 그래서 토큰 만료 10분 전이 되면 각 프로세스가 각자 재발급하다가 부딪히고,
  실패한 프로세스는 요청이 올 때마다 다시 발급을 시도한다.
- 운영 도메인(yangbong-store.chagoklabs.com)의 `/api` 는 아직 **옛 비밀상회 서버**다. 근거: 로그인 없이 news 생성이 되고,
  `/master/batch-jobs` 가 200 으로 응답한다. 양봉 서버(APP_SERVICE=yangbong, d67dc9d 이후 코드)로 전환하는 일이 이 설계보다 먼저다.
- AI 생성(웹서치 포함)은 한 건에 수십 초가 걸린다. 지금은 HTTP 요청 안에서 동기로 기다리므로(gunicorn timeout 180s)
  여러 사람이 동시에 누르면 워커가 묶이고, 같은 종목을 여럿이 누르면 같은 생성이 중복 실행된다.

## 1. 확정 사항 (2026-11-18)

| 항목 | 결정 |
|---|---|
| 작업자 위치 | **양봉 전용 AI 워커 컨테이너**(같은 이미지, 프로세스 1개) |
| 완료 알림 | **앱 내 알림 + 푸시** 동시 |
| KIS 사용 | **AI 워커만 KIS 사용.** API 서버는 KIS_ENABLED=false 유지 |

## 2. 전체 흐름

```
사용자 ─POST 요청─▶ 양봉 API ─(검증·한도·중복합치기)─▶ stock_ai_job (QUEUED)
                       │ 202 {job_id, 대기순번}
                       ▼
화면: "분석 요청됨 · 대기 n번째"  ◀─ 5초 폴링(화면 보는 동안만) ─ GET job

AI 워커(1 프로세스) ─ SKIP LOCKED 로 가져옴 → RUNNING
   ├ KIS 조회(뉴스 헤드라인·재무) — PyKis 1개, 토큰 1개
   ├ Anthropic 호출 (동시 N건)
   ├ stock_ai_content 저장 → DONE
   └ 구독자마다 user_notification 기록 + FCM 푸시
```

## 3. DB (sql/yangbong/008_ai_job.sql)

**stock_ai_job** — 생성 작업 1건

| 컬럼 | 설명 |
|---|---|
| job_id PK | |
| stock_code, section | section = overview / theme / news / finance |
| status | QUEUED / RUNNING / DONE / FAILED |
| created_by | 처음 요청한 user_id (news 자동 갱신이면 NULL) |
| force | 관리자 쿨다운 우회 |
| attempts | 재시도 횟수 |
| error_user | 사용자에게 보여 줄 문구 |
| error_detail | 원문(로그용, API 로는 내보내지 않음) |
| created_at, started_at, finished_at | |
| active_key | 생성 컬럼 `IF(status IN ('QUEUED','RUNNING'), CONCAT(stock_code,':',section), NULL)` 에 **UNIQUE** 를 건다. 같은 종목·섹션의 진행 중 작업은 1건만 존재 |

**stock_ai_job_subscriber** — 같은 작업을 기다리는 사람들 (job_id, user_id, created_at) PK(job_id, user_id)

- 이미 진행 중인 작업이 있으면 새로 만들지 않고 구독자로만 붙는다(AI 비용 1회).
- 하루 한도(stock_ai_gen_log)는 **작업을 새로 만든 사람만** 차감한다. 구독만 한 사람은 차감하지 않는다. 실패하면 환불(기존 규칙 유지).

**user_notification** — 앱 내 알림함

| 컬럼 | 설명 |
|---|---|
| notification_id PK, user_id | |
| type | AI_DONE / AI_FAILED (이후 다른 알림도 이 표로) |
| title, body | |
| link | 예: `/stock/info?stock_code=005930&tab=basis` |
| ref_id | job_id |
| created_at, read_at | |

**stock_finance_snapshot** — 재무 지표 캐시 (stock_code PK, data JSON, fetched_at)
- API 서버는 KIS 를 부르지 않으므로, 재무 탭은 이 표를 읽는다. 없거나 오래되면 finance 작업을 넣는다(AI 비용 없음, 한도 차감 없음).

`yangbong.device_push_token` 은 이미 있다(002). 권한(GRANT)은 008 에 같이 넣는다.

## 4. API (양봉 서버, 모두 로그인 필요)

| 메서드·경로 | 동작 |
|---|---|
| `POST /api/v1/anthropic/stock-analysis/{section}/jobs` `{stock_code, force?}` | 쿨다운·실적발표월·하루 한도를 **동기로** 검사 → 위반이면 409/429. 통과하면 작업 생성(또는 구독) 후 **202** `{job_id, status, queue_position, joined}` |
| `GET /api/v1/anthropic/stock-analysis/jobs?stock_code=` | 이 종목에서 내가 기다리는 작업(화면 재진입 시 상태 복원) |
| `GET /api/v1/anthropic/stock-analysis/jobs/{job_id}` | 상태·대기순번·error_user |
| `GET /api/v1/anthropic/stock-analysis/{overview\|theme\|news}` | **DB 만 읽는다**(생성하지 않음). news 가 2시간 지났으면 `stale: true` 를 붙이고 서버가 news 작업을 자동으로 넣는다(구독 없음, 한도는 서버 전체에만 집계) |
| `GET /api/v1/stocks/id/{code}/finance` | stock_finance_snapshot 을 읽는다. 없거나 10분 지났으면 finance 작업을 넣고 `{pending: true}` |
| `GET /api/v1/notifications?page=&size=` | 알림 목록 + `unread_count` |
| `PATCH /api/v1/notifications/{id}/read`, `POST /api/v1/notifications/read-all` | 읽음 처리 |
| `POST /api/v1/notify/register`, `POST /api/v1/notify/unregister` | 푸시 토큰을 yangbong.device_push_token 에 기록. **배치 서버로 가던 등록(C-1)을 여기로 옮긴다** |

오류 응답에는 KIS·Anthropic 원문을 넣지 않는다. 원문은 서버 로그와 error_detail 에만 남긴다.

## 5. AI 워커 (yangbong-ai-worker 컨테이너)

- 실행: 같은 이미지, `python -m app.workers.ai_job_worker`, `APP_SERVICE=yangbong`, `KIS_ENABLED=true`(이 컨테이너만).
- KIS 키: 양봉 DB 에는 KIS 키가 없다(005 에서 제외). 워커 전용 env 파일이나 마운트 파일에서 읽는다. 양봉 API 컨테이너에는 넣지 않는다.
- 가져오기: `SELECT … WHERE status='QUEUED' ORDER BY created_at LIMIT k FOR UPDATE SKIP LOCKED` → RUNNING.
  우선순위는 사용자 요청(overview/theme) > finance > news 자동.
- 동시 실행: 스레드풀 N건. 값은 공통코드 `stock/setting/ai` 의 `AI_WORKER_CONCURRENCY`(기본 3). 공통코드 → env → 기본값 순.
- KIS: 프로세스 안에 PyKis 1개. EGW00133 이 나면 61초 기다렸다가 캐시 파일을 다시 읽고 재시도한다.
- 복구: 워커가 뜰 때 10분 넘게 RUNNING 인 작업은 attempts < 2 면 QUEUED 로 되돌리고, 아니면 FAILED 로 바꾸고 환불·실패 알림.
- 완료: stock_ai_content 저장 → DONE → 구독자마다 user_notification 기록 → FCM 푸시.
  푸시 본문 예: "삼성전자 AI 견해가 준비됐어요". 탭하면 link 로 이동.
- 푸시 발송: py-stock-batch 의 `PushSender`(firebase_admin) 를 `stock_shared` 로 옮겨 같이 쓴다.
  Firebase 서비스 계정 파일은 워커에만 마운트한다.

## 6. 화면 (yangbong-store-vue)

- StockInfo AI 견해 탭
  - 새로고침 → POST jobs → 버튼 자리에 "분석 요청됨 · 대기 n번째" / "분석 중…" 표시.
  - 화면을 보고 있는 동안(visibilitychange)만 5초 간격으로 job 을 폴링한다. DONE 이 되면 내용을 다시 읽는다.
  - 다른 화면으로 나가도 작업은 계속된다. 재진입하면 `GET jobs?stock_code=` 로 상태를 복원한다.
  - 재무 탭: `pending` 이면 "불러오는 중"을 띄우고 짧게 폴링한다.
  - 오류 문구는 서버가 준 사용자용 문구만 보여 준다.
- 알림함: 헤더에 알림 아이콘과 읽지 않은 수(뱃지 금지 규칙 → 숫자 글자색만), 알림 목록 화면 `/notifications`.
  읽지 않은 수는 라우트 이동·앱 복귀 때 다시 읽는다.
- 푸시: `usePushNotifications` 의 등록 대상을 batchApi → aibeesApi(`/api/v1/notify/register`)로 바꾼다.
  알림을 탭하면 data.link 로 이동한다.

## 7. 배포 순서

1. **(선행)** 운영 도메인 `/api` 를 양봉 서버(APP_SERVICE=yangbong)로 전환한다. 보안 구멍이 열려 있으므로 가장 먼저 한다.
2. sql/yangbong/008 적용 → 테이블 존재 확인(마이그레이션 미적용 함정).
3. 양봉 API 컨테이너 재배포 + AI 워커 컨테이너 기동(boot 로그 시각으로 확인).
4. 웹 배포.
5. 앱 새 빌드(앱은 웹 빌드를 내장하므로 푸시 등록 경로 변경은 새 빌드부터 반영).

## 8. 미결

- 워커 동시 실행 수 N 과 하루 한도(GEN_PER_USER_DAY 5 / GEN_TOTAL_DAY 100) 값.
- 대기 중인 작업을 사용자가 취소할 수 있게 할지(현재 설계: 취소 없음).
- 비밀상회 서버의 같은 토큰 충돌: 비밀상회는 이 설계 범위 밖이다.
  KisEngine 에 "EGW00133 이면 캐시 파일 재로드 후 재시도"만 따로 넣을지는 별도로 정한다.
